## Invitations, registration and reset now end in the app

An invitation, a self-registration or a password reset that starts in an app now
sends the user back to that app through OpenID Connect Core 1.0 §4 (Initiating
Login from a Third Party), instead of leaving them on Stargate's login page.

- OAuth clients carry `initiate_login_uri`, the app endpoint that starts a
  login: `initiateLoginUri` in the admin API (read, create, update and patch) and
  in the Console's client forms. It follows the same URL rules as
  `backchannel_logout_uri`: absolute HTTPS, or loopback HTTP for development, and
  no fragment.
- `POST /admin/users/invitations` accepts `clientId` and `targetLinkUri`. The
  client must exist, be enabled and register `initiate_login_uri`, otherwise the
  request fails with `400 signup.invitation_client_invalid`; `targetLinkUri` is
  an absolute HTTPS URL accepted only together with `clientId`.
- `POST /signup` and `POST /account/credentials` accept `interactionId`, the
  parked authorization request the app derived from its `return_to`. A missing or
  expired interaction means no continuation and no error, and both responses stay
  identical for known and unknown addresses.
- `PUT /signup` and `PUT /account/credentials` return `continueUrl` and
  `clientName` while the client is still enabled. The URL is built on the server
  from `initiate_login_uri` with `iss`, `login_hint` and, for an invitation,
  `target_link_uri`. The hosted auth app then offers "Continue to <app>" instead
  of "Go to Login".

There is no automatic sign-in: the app receives the user and starts a normal
authorization request. `docs/oauth-oidc-provider-guide.md`, "Login Initiated by
a Third Party", describes both sides.

## Database migration

`20261116000000_oauth_client_initiate_login_uri` adds a nullable
`initiate_login_uri` column to `oauth_clients`, for PostgreSQL and SQLite. Server
startup applies it by default; with `DB_MIGRATE_ON_START=false` run
`stargate db migrate` before starting this version. Existing clients keep working
without the column filled and earlier replicas ignore it, so the upgrade has no
required order.

## Operator steps

1. Register the endpoint of every app that invites users or starts
   registrations and resets: set `initiateLoginUri` on its OAuth client, in the
   Console or through `/admin/oauth/clients`.
2. Implement that endpoint in the app: verify `iss`, start `/oauth/authorize`
   with `login_hint`, its own `state` and PKCE, and accept `target_link_uri` only
   when it points at the app itself.
3. Where invitations are sent, pass `clientId` and, when the user should land on
   a specific page after the login, `targetLinkUri`.

## Password resets pending during the upgrade

`change_password_requests:{email}` stores `{sid, continuation}` instead of the
bare reset id. A reset requested by the previous version cannot be read by this
one, so `POST /account/credentials` for that address fails with `500` until the
record expires, one hour at most. Ask those users to request the reset again; no
state migration is needed.
